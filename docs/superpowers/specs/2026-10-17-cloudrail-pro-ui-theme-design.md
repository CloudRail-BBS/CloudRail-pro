# CloudRail-pro 全量 UI 主题与视觉统一设计

日期：2026-10-17

状态：聊天中已确认设计，待用户审阅本说明

## 背景与目标

CloudRail-pro 是 uni-app 社区前端。当前样式以浅色为主，页面与组件中散布大量固定颜色；自定义 TabBar 会局部读取系统深色，但页面没有统一主题状态。项目目前注册了 104 条页面路由（103 个 `.vue` 页面及 1 个 `.nvue` 页面），另有 `pages/video/overlay.nvue` 作为播放器子视图，需要一并覆盖。

目标是在全量页面和自有组件中建立连贯的浅色、深色 UI，默认跟随系统，同时允许用户固定浅色或深色。全量统一基础表面、文字、表单、按钮、导航和状态表达，并提升页面层级、列表分组和移动端触达一致性。此工作仅调整前端视觉与主题偏好，不改变接口、权限、数据和业务流程。

## 方案选择

考虑了三种方式：

1. **只覆盖全局样式。** 改动少，但页面 scoped 样式会覆盖 App 全局规则，不能可靠改变现有页面；不采用。
2. **逐页自由重做。** 可为每页单独优化，但长期会产生新的色彩、控件和间距差异；不采用。
3. **统一语义主题、按页面域迁移。** 以一个主题状态和语义色板为共同基础，迁移每个页面的局部样式，同时保留游戏和媒体等内容专属视觉；采用此方案。

## 主题偏好与运行状态

主题偏好为 `system`、`light`、`dark`，默认 `system`。主题设置位于 `pages/user/setting.vue` 的“外观”分组，并采用单选控件。切换立即生效，偏好写入本机存储，不依赖服务器账号或网络。

主题管理模块是唯一状态源，负责读取和保存偏好、解析有效主题、监听环境变化、通知当前页面和组件刷新。应用启动时先读取保存值再首屏渲染，避免浅色闪屏；没有保存值时按系统主题启动。用户选 `system` 时，系统变化会更新有效主题；用户选定 `light` 或 `dark` 后，系统变化不覆盖手动选择。应用恢复前台时重新检查系统主题，确保不支持实时通知的平台也能同步。

系统主题读取按运行平台适配：H5 使用浏览器主题媒体查询；App 和微信小程序使用 uni-app 的系统主题信息及主题变化事件；支付宝、百度、抖音等当前未提供相同主题变化事件的平台，在启动和回到前台时重新读取系统状态。无法读取系统主题时仅对 `system` 偏好回退浅色，不修改用户保存的手动选项。监听器由应用级主题模块注册一次，并在适用处正确注销，避免页面切换导致重复监听。

平台原生导航及安全区域使用 uni-app 支持的 `darkmode` / `themeLocation` / `theme.json` 配置；因绝大多数页面采用自定义导航，导航栏、状态栏、TabBar 等实际运行时颜色仍由主题模块及自有导航组件同步。主题内容样式不依赖单独改 `uni.scss` 或 `pages.json`。uni-app 页面局部样式会覆盖 App 全局样式，nvue 也有独立样式限制，因此 Vue 页面、共享组件与 nvue 子视图分别迁移并验证。平台主题能力与 CSS 范围遵照 [uni-app 暗黑模式适配](https://uniapp.dcloud.net.cn/tutorial/darkmode.html)、[uni-app 样式与布局](https://uniapp.dcloud.net.cn/tutorial/syntax-css.html) 和 [uni.onThemeChange 兼容性](https://uniapp.dcloud.net.cn/api/system/theme.html) 处理，不假定所有目标平台的 CSS 或主题监听能力完全相同。

## 视觉语言

页面沿用用户确认的 B 类 Quiet Cards：浅色用浅灰页面画布承托白色内容面板；深色使用黑色画布和分层深灰表面。卡片用于适合分组的内容；设置与管理列表优先用清晰分组及细分隔线，避免每一项都套相同卡片和阴影。

| 语义 token | 浅色 | 深色 |
| --- | --- | --- |
| 页面画布 | `#fafafa` | `#0a0a0a` |
| 主表面 | `#ffffff` | `#111111` |
| 次表面 | `#f2f2f2` | `#1a1a1a` |
| 选中 / 按压表面 | `#ebebeb` | `#1f1f1f` |
| 主文字 | `#171717` | `#ededed` |
| 次级文字 | `#666666` | `#a1a1a1` |
| 弱分隔线 | `#e0e0e0` | `#2e2e2e` |
| 强分隔线 | `#c9c9c9` | `#454545` |
| 危险 | `#da2f35` | `#ff6166` |
| 成功 | `#297c3b` | `#62c073` |

黑白作为主要操作色；红、绿只承担危险和成功等语义。现有 Noto Sans SC 中文字体体系保留，统一页面标题、分区标题、正文、说明文字的字级、字重和行高。统一常用页面留白、内容分组、边框圆角、列表触控区、输入框和按钮尺寸。反馈、禁用、焦点及选中状态需在两套主题下清楚可辨。

保留内容本身的色彩：游戏桌面、牌面和胜负状态；VIP/商品权益插画；抽奖奖级；头像、帖子/商品封面、应用图标、视频画面和媒体叠层。它们周围的页面画布、文本、通用操作和弹层仍遵循主题语义。业务状态颜色只在确有状态含义时保留，危险/成功映射到上述语义色。

## 覆盖范围与迁移边界

- 覆盖 `pages.json` 的全部 104 条注册路由、`pages/video/overlay.nvue`、App 级样式与自有 `components/**`。
- 按首页/社区内容、消息、个人资料与设置、登录注册、市场与软件、管理后台、媒体与游戏等功能域迁移。
- 处理自定义导航、系统状态栏、安全区、TabBar、表单、弹窗、遮罩、加载/空态与动态 inline 样式。
- 保留接口、权限、路由和业务逻辑；不改第三方服务端或加入服务端主题同步。
- 第三方库的内部样式不做无关重构；若其控件出现在主题页面中，优先通过自有封装、属性和外围表面保持可读性。

实现时先确认所有页面根节点和组件样式边界。建立明确的语义 token 与可跨目标验证的主题应用方式，再按域替换硬编码颜色。H5、App、小程序与 nvue 的运行时样式能力不一；不要依赖仅 H5 可写的 `document` 修改来驱动全端主题，也不把 Sass 编译变量当作可运行时切换的值。页面局部 scoped 样式和播放器覆盖层应具有明确的浅/深态处理。

## 实施顺序

1. 增加主题偏好/有效主题模块、平台适配、主题配置及解析逻辑验证。
2. 接入启动与前后台生命周期；同步自定义 TabBar、通用导航和系统栏。
3. 在设置页增加“跟随系统 / 浅色 / 深色”选项，并验证偏好持久化和即时切换。
4. 迁移共享组件与全局页面基础，再逐域迁移所有页面的表面、文本、边框、表单和交互状态。
5. 单独处理游戏/VIP/商城/抽奖/视频内容色彩、`douyin.nvue` 与 `overlay.nvue`。
6. 按路由清单做遗漏扫描，修正两套主题中的对比度与层级问题。

## 验收与验证

- 自动验证主题解析：默认 `system`；合法手动偏好覆盖系统；系统事件仅在 `system` 模式改变有效主题；无系统信息时回退浅色；存储损坏或未知偏好安全回退。
- 验证偏好冷启动读取、设置页即时切换与本机持久化、主题事件监听不重复；覆盖 H5 媒体查询及可用原生系统主题事件。
- 通过脚本/静态检查核对所有 104 条注册路由、播放器子视图和自有组件的迁移状态；搜索遗留硬编码中性背景/文字色，并人工判断保留的内容色是否有明确语义。
- 检查首页、圈子/动态、消息与聊天、个人中心/设置、登录、管理页、商品、游戏、媒体播放器和 nvue 覆盖层的浅/深色显示，特别检查自定义导航、系统栏、底部安全区、表单、弹层、文本对比和图片/视频原色。
- 运行仓库可用的单元测试、配置 JSON 校验和平台构建/预览。当前根 `package.json` 没有常规应用构建脚本；若环境无法运行 HBuilderX 平台构建，需明确报告该限制，并提供可复现的静态检查和实际可运行平台验证结果。

完成标准：所有注册页面和自有 UI 组件可在系统、浅色、深色偏好下正常使用；偏好行为符合本说明；通用页面层级和控件在两种主题保持一致；专属内容色与业务行为未被错误改动；验证结果及未能运行的平台检查有清楚记录。
